# CLI workflows

The `margo` command turns a Markdown source or directory into an inspectable
artifact. Reports and generated bytes have explicit destinations: diagnostics
go to stderr, while ordinary command output goes to stdout or a declared file.

## Install and check the version

Install a pinned release in the environment that owns the build, then verify
the binary before using it in automation:

```sh
go install github.com/araihu/margo/cmd/margo@vX.Y.Z
margo version
margo check guide.md --diagnostics json
```

`version` reports release and compiled capability information. `check` validates
compatibility without publishing an output artifact.

## stdin, stdout, and stderr

Commands that render one document read the explicit input path, or stdin when a
command documents that behavior. HTML and deck output can go to stdout by
default; PDF output requires `--output` or `-` for binary stdout. Diagnostics
never mix with generated bytes, so scripts can pipe artifacts safely.

Exit status is non-zero for invalid input, policy failures, unavailable engines,
or protected output destinations. JSON diagnostics preserve stable codes,
source paths, and remediation hints for CI.

## Command map

| Command | Purpose |
| --- | --- |
| `check` | Validate Markdown compatibility and report findings |
| `html` | Render one standalone HTML page |
| `pdf` | Export one document through a selected local engine |
| `deck` | Produce an experimental HTML or PDF presentation |
| `site` | Build linked HTML pages from a directory or `site.yaml` |
| `serve` | Preview a directory/config with live reload |
| `doctor` | Inspect available PDF engines and capabilities |
| `schema` | Emit the embedded document or policy schema |
| `version` | Report release and compiled capability identity |
| `completion` | Generate shell completion for the command surface |

## Configuration and policy layering

`site.yaml` owns source/output paths, typed layouts, navigation, themes, base
paths, canonical identity, and artifact staging. Document frontmatter carries
closed metadata and publication actions. Explicit CLI or API options take
precedence where the contract allows it; host policy remains authoritative for
raw HTML and iframe projections.

```sh
margo site ./showcase.yaml
margo html guide.md --policy policy.json --diagnostics json
```

The configured site builder preflights routes and dependencies before emitting
artifacts. `offline: true` plus local assets keeps the result self-contained.

## Output replacement safeguards

Margo does not silently replace an existing file. Pass `--force` when replacing
one explicitly. A configured site destination must not already exist; build a
complete staged result before publication. These boundaries keep a typo or
failed rebuild from destroying a previous artifact.

## Operational gotchas

- `serve` binds to loopback by default and has no TLS, authentication,
  authorization, or rate limiting; it is a development preview.
- `pdf` and `deck` discover an installed Chromium-family engine but do not
  download one. Run `doctor` before depending on local PDF output.
- Relative links, image paths, source names, and output paths are validated;
  missing targets fail the build instead of producing a partial site.
- `site.yaml` is read from the requested directory/config path, and generated
  output is kept outside the configured source tree.
